# Architecture decisions

One entry per significant decision. Format: context, decision, alternatives, consequences. Newest at the bottom.

## D-001: Monorepo tooling versions (2026-10-22, Orchestrator)

- **Context:** CLAUDE.md §3 fixes the stack (TypeScript, pnpm workspaces, Vitest, ESLint + Prettier, `node:sqlite`). Exact versions were open.
- **Decision:** TypeScript 6.0.x (not 7.x: `typescript-eslint` 8.72 supports `<6.1`), ESLint 10 flat config, Vitest 5 with `test.projects`, Vite 8 + React 19 for the simulator UI, `tsx` for running TypeScript scripts, `@anthropic-ai/sdk` 1.1.0. All pinned exactly. Workspace packages export their `src/index.ts` directly (no build step; Vitest, Vite and tsx consume TypeScript source).
- **Alternatives:** TypeScript 7 (native), building packages to `dist/` with project references.
- **Consequences:** No build step for the library packages, which keeps the loop fast. If a published build is ever needed, add `tsc -b` with `outDir` later.

## D-002: pnpm 12 inside the sandbox (2026-10-22, Orchestrator)

- **Context:** `pnpm install` failed with `ERR_PNPM_STORE_DIR_OPEN_OPERATION_LOCK: Operation not permitted`. pnpm 12 (a Rust binary from Homebrew) opens its store locks under `$XDG_RUNTIME_DIR`, which defaults to a location outside the repo that the sandbox cannot write.
- **Decision:** Every shell that runs pnpm in the sandbox sets `XDG_RUNTIME_DIR="$PWD/.cache/runtime"` (added to `scripts/overnight.sh`; builder prompts include it). Store and cache dirs are set in `pnpm-workspace.yaml` (pnpm 12 ignores the `pnpm` field in `package.json` and `store-dir` in `.npmrc`). `verifyDepsBeforeRun` is off so scripts don't trigger hidden installs. Build scripts are allowed only for `esbuild` via `allowBuilds`.
- **Alternatives:** Install pnpm 10 (can't: no installs outside the repo), use npm (loses workspace ergonomics).
- **Consequences:** Running pnpm from a fresh shell without the env var fails with the lock error; the fix is one `export`.

## D-003: Package map and import direction (2026-10-22, architect)

- **Context:** CLAUDE.md §3 names five packages; builders need a hard rule about who imports whom so parallel tasks don't tangle.
- **Decision:** `core` imports nothing internal and nothing but Node built-ins; `adapters` imports `core`; `agent` imports `core` + `adapters` + the Anthropic SDK; `evals` and `apps/simulator` import all. `core` exports function modules as namespaces (`ledger`, `approval`, `audit`, `flights`, `safety`, `recaps`) and everything else top-level. `Money` uses the field name `amountMinor` (the adapter interfaces and SAFETY.md already use the `*Minor` convention; VOICE §5's `amount` is the same value). The adapter interfaces now import primitives (`Money`, ids, ISO types, `Clock`, `ContentTag`, `ConsentLookup`, `ParsedReceipt`) from `@trav/core`; adapter-only shapes (`AdapterInfo`, `ApprovalProof`, `AdapterError`, `Result`) stay in `adapters/interfaces/common.ts`. The adapters' Plaid-shaped row is renamed `ProviderTransaction` so core's `Private<CardTransaction>` keeps the SAFETY name.
- **Alternatives:** A separate `types` package (one more package for no gain); letting adapters keep duplicate primitives (two `Money` types to convert between).
- **Consequences:** Builders in `core` can't reach for an adapter; the simulator and evals are the only composition points.

## D-004: `BookingExecutor` lives in `packages/agent/src/booking/executor.ts` (2026-10-22, architect)

- **Context:** SAFETY §2.1 requires exactly one call site for provider `purchase`/`createOrder`/`book` and payments `charge`, re-checking the grant and writing audit/ledger in order.
- **Decision:** The executor is `createBookingExecutor(deps)` in `packages/agent/src/booking/executor.ts`. Core stays pure (it supplies `approval.checkGrant`, `deriveIdempotencyKey`, repositories); adapters supply providers; the executor is the only importer of their money-moving methods. The architectural grep test (T-054) asserts that `.purchase(`, `.createOrder(`, `.book(` and `.charge(` each have exactly one non-test call site, in that file. `ApprovalHandler` (`agent/approval/handler.ts`) is the only caller of `execute()`.
- **Alternatives:** Executor in `core` (would force I/O into core); executor in `adapters` (adapters would need policy knowledge).
- **Consequences:** Flow 2 in ARCHITECTURE.md is the spec for T-009; providers export factories only.

## D-005: Default `paidBy` is `member_card` (2026-10-22, architect)

- **Context:** VOICE §4.1 defaults to "charged to Dean's card, split 5 ways on the tab"; the alternative is charging each attendee's mock card.
- **Decision:** v0 default for tickets, lodging and transport is `{ kind: 'member_card', memberId: requestedBy }`: one mock charge to the requester, an `Expense` split among `payers` on the ledger. `{ kind: 'per_person_cards' }` remains in the `PaidBy` union and is the default for `flight` (each on their own card, "nothing to split"; the ledger records nothing). Both proposal and receipt cards carry `paidBy`.
- **Alternatives:** Per-person cards everywhere (no ledger activity, weaker demo); a group pot (no such thing in v0).
- **Consequences:** The Razzmatazz flow exercises ledger split + settle-up; the flights flow exercises `each_payer` approval without ledger entries.

## D-006: Offline mode keys and replays scripted model responses (2026-10-22, architect)

- **Context:** All agent logic must run deterministically with `TRAV_OFFLINE=1` and no key; new scenarios should still produce sensible behavior without hand-authored scripts.
- **Decision:** One `ModelClient` (`agent/model/client.ts`) with `complete()` and `classify()`. Offline lookups use `deriveScriptKey = sha256(model, systemPromptId, normalized last user text, sorted tool names)` against `fixtures/scripts/*.json`; misses go to ordered rule-based `FallbackResponder`s (mention rules, "looks shared" heuristics, booking-intent regex, receipt fixture lookup, roast blocklist), then a fixed "not sure" reply plus a line in `.trav/offline-misses.jsonl`. Live calls go through a spend guard writing `.trav/spend.json` and refusing past `TRAV_LIVE_BUDGET_USD`. Any request with an `<untrusted` block and non-empty tools throws in both modes.
- **Alternatives:** Keying on the full prompt hash (breaks on every prompt tweak); a recording proxy only (no behavior for unscripted inputs); mocking the SDK per test (no shared path to audit).
- **Consequences:** Prompt ids (`systemPromptId`) must be stable strings; changing a template's id invalidates its scripts on purpose. Scripts are reviewed like code.

## D-007: Private vs group separation is structural (2026-10-22, architect)

- **Context:** SAFETY §2.3 asks for separation enforced by types and stores, not prompts.
- **Decision:** `Private<T>` brand in `core/privacy.ts`; `PrivateStore` methods take `ownerMemberId` first with no list-all (only `countPendingByOwner` crossed owners, returning counts; removed by D-031); `GroupContext` is built from unbranded types; `GroupSafe<T>` + `assertGroupSafe()`/`withExtra()` reject branded values at compile time (proved in `core/src/privacy.test.ts`); `promote()` is the single private → group function and strips `STRIPPED_FIELDS`. Ticket QR artifacts are stored in `PrivateStore.ticket_artifacts` (the group store keeps only `TicketRef`s), so a barcode can never be rendered on the group lane. Group memory (`GroupMemoryRepository`, GroupStore) and member memory (`PrivateStore.memberMemory`) are separate modules in `agent/memory`.
- **Alternatives:** One store with a `visibility` column (a missed `WHERE` leaks); prompt instructions (not enforceable).
- **Consequences:** Builders of ingestion flows must mark rows with `markPrivate()` and can only hand the group an `Expense` from `promote()`.

## D-008: One injected `Clock`, one `Scheduler`, no `Date.now()` in domain code (2026-10-22, architect)

- **Context:** Recaps, proposal expiry, holds, offer expiry and nudges must move together under the simulator's "+1 hour" / "next morning" buttons and be deterministic in tests.
- **Decision:** `core/clock.ts` defines `Clock`, `SimulatedClock`, time helpers, `ScheduledJob`/`Scheduler`. Every function needing time takes a `Clock` or an explicit instant. An ESLint `no-restricted-syntax` rule (root `eslint.config.js`) forbids `Date.now()` and `new Date()` under `packages/*/src` and `apps/*/src`, except `clock.ts`, tests and `core/src/storage/**`. The clock owner (simulator, CLI, evals) calls `scheduler.drain(clock.now())` after advancing and feeds jobs to `agent.runScheduled`.
- **Alternatives:** `vi.useFakeTimers` (does not reach the simulator UI or SQLite timestamps); a global mutable clock (hidden coupling).
- **Consequences:** Entry points construct the clock once; mocks and repositories receive it in their factories.

## D-009: Channel lanes, one `ApprovalEvent`, budget guard as a channel decorator (2026-10-22, architect)

- **Context:** VOICE §3.7 needs a group lane and a private DM lane; VOICE §9.3 wants one approval code path for tapbacks, text aliases and buttons; G-03 caps proactive group messages.
- **Decision:** `ChannelAdapter` has `sendGroup(conversationId, OutboundMessage)` and `sendDirect(handle, OutboundMessage)` (both take core `OutboundMessage`; adapters degrade cards to `text`), `react(OutboundReaction)`, and a `lane` on every inbound event. connector-scout's `sendText`/`sendCard` and its own `RichCard` are replaced by core's `Outbound` types. All approval inputs normalize in `agent/approval/events.ts` (`normalizeApprovalEvent` → `ApprovalEvent { kind: ActionId, senderId, via, messageId, cardId?, proposalId? }`) and are consumed by one `ApprovalHandler`. The message-budget guard is a decorator `withMessageBudget(channel, …)` in `adapters/channel/budget.ts` keyed on `OutboundMessage.proactive`/`urgent`, so it is built and tested in T-006 without touching the agent; `screenOutbound` + the voice linter run in the agent's single send path `agent/outbound/send.ts`.
- **Alternatives:** Budget in the agent (couples T-006 to T-007); separate handlers per input kind (three places to get identity wrong).
- **Consequences:** Adapters never see `Private<T>`; a DM-only card handed to `sendGroup` is rejected twice (screen, then adapter).

## D-010: Errors, idempotency and audit naming conventions (2026-10-22, architect)

- **Context:** Builders need one convention per layer.
- **Decision:** Core throws `TravError(code)` for invalid input/invariants and returns domain outcomes as values; adapters return `Result<T>` with `AdapterError` for expected failures; the agent converts both into VOICE §4.10 text at the turn boundary. Idempotency: booking key per SAFETY §2.1 (`approval.deriveIdempotencyKey`), checked before evaluation, in the executor, at the provider and in `BookingRepository.createBooking`; ledger writes unique on `Expense.sourceRef`; grants idempotent per member; inbound dedupe by `messageId`; scheduler jobs replace by `jobId`. Audit events are named `<entity>.<state>` in snake_case and listed in `core/domain/audit.ts`; repositories reject payloads containing `audit.PRIVATE_PAYLOAD_KEYS`. Repositories are synchronous (`node:sqlite` is synchronous; keeps the shared suite simple).
- **Alternatives:** Exceptions everywhere (hides expected provider failures); `Result` in core (noise in pure math); async repositories (no benefit in v0).
- **Consequences:** Adapter tests assert on `error.code`; core tests assert on thrown `TravError.code` or returned decisions.

## D-011: Ids from an injected `IdGenerator`, ulid-like, prefixed (2026-10-22, architect)

- **Context:** Deterministic tests and fixtures; no new dependency.
- **Decision:** `core/ids.ts`: `IdGenerator.next(prefix)` returns `<prefix>_<body>` where the ulid body is 26 Crockford chars and the deterministic body is `<seed><6-digit counter>` (e.g. `mem_bcn000001`, readable in fixtures); `createDeterministicIdGenerator(seed)` (counter per prefix) for tests/fixtures, `createUlidIdGenerator(clock)` (time from the injected clock + `node:crypto` randomness) at runtime. Prefix table in `ID_PREFIXES`.
- **Alternatives:** the `ulid` npm package (one more dependency for 20 lines); `crypto.randomUUID()` inline (non-deterministic tests, unprefixed ids).
- **Consequences:** Snapshot tests are stable; ids are greppable by kind.

## D-012: Roles unify VOICE §6.1 and SAFETY §2.5; "minor" is a predicate (2026-10-22, architect)

- **Context:** VOICE lists `lead | member | guardian | minor`; SAFETY lists `member | guest`.
- **Decision:** `Member.role ∈ lead | member | guardian | guest`. Minority is `safety.isMinor(member, now)` from `birthDate`/`ageBand` (unknown age ⇒ not minor for content, but roast blocked until `settings.allAdultsConfirmed`). `approval.toMemberView()` maps lead/guardian/member → `'member'`, guest → `'guest'`. Minors keep `guardianMemberId` for ticket delivery and the family tab.
- **Alternatives:** A `minor` role (ages change; a role can be forgotten when a birthday passes).
- **Consequences:** One source of truth for every age rule; the T-028 predicates are the only place age is interpreted.

## D-013: Consent map is passed to the album adapter; `ApprovalProof` is derived from the core grant (2026-10-22, architect)

- **Context:** ideation asked for the album adapter to take a consent map rather than own consent; connector-scout's providers require an `ApprovalProof` the core types did not define.
- **Decision:** Consent is stored once in `PrivateStore.consent`; `AlbumAdapter.listPhotos(query, consentLookup)` filters at query time with the lookup passed in (so opt-out hides photos from re-rendered recaps), and `hidePhoto()` implements "drop that one" for any member. `ApprovalProof` stays an adapter-side opaque shape produced only by `toApprovalProof(grant, decision, proposal, grantedAuditEventId)` in the executor (`approvalId = grantId`).
- **Alternatives:** Adapter-owned consent (two sources of truth); passing the core grant to adapters (adapters would import policy types).
- **Consequences:** Album tests inject a consent lookup; provider mocks validate proofs without knowing the policy.

## D-014: Storage is a subpath export, `@trav/core/storage` (2026-10-22, Orchestrator)

- **Context:** T-005 implemented the repositories under `packages/core/src/storage/` using `node:sqlite`. The simulator's browser UI imports `@trav/core` for types and pure functions; `node:sqlite` cannot be bundled for the browser.
- **Decision:** `packages/core/package.json` exports `./storage` → `src/storage/index.ts` separately. Node entry points (agent runtime, CLI, evals, simulator server) import `@trav/core/storage`; the root `@trav/core` export stays free of Node-only modules.
- **Alternatives:** export storage from the root index (breaks Vite bundling of the UI); a separate package (more boilerplate).
- **Consequences:** `createMemoryStores`/`createSqliteStores` are imported from `@trav/core/storage`.

## D-015: TypeScript scripts run with `node --import tsx`, not the `tsx` binary (2026-10-22, Orchestrator)

- **Context:** T-055 found that the `tsx` CLI fails inside the overnight sandbox with `listen EPERM` because it opens an IPC pipe under the temp dir that Seatbelt refuses. `node --import tsx file.ts` loads the same loader in-process and works.
- **Decision:** Every package script that runs TypeScript directly (`audit:verify`, `demo:barcelona`, `sim` server, `eval`) uses `node --import tsx <file>`. Arguments pass through unchanged.
- **Alternatives:** compile scripts with `tsc` first (slower loop); `node --experimental-strip-types` (Node 25 supports it, but workspace `.ts` imports via package `exports` and `verbatimModuleSyntax` make tsx the safer choice for now).
- **Consequences:** Outside the sandbox both forms work; inside, only this one does.

## D-016: Audit hash commits to the payload digest; lifecycle facts live in the hashed header; the chain is anchored externally (2026-10-22, builder T-004/T-055)

- **Context:** SAFETY §2.2 wrote the hash as "sha256(prevHash + canonical JSON of everything above)" and §2.9 said redaction replaces the payload with `{ redacted: true }` while hashes stay as stored. Taken literally, a redacted row can no longer be recomputed, so the verifier would have to trust its stored hash, and then any single-row payload edit to `{ redacted: true }` passes, and a tombstoned `approval.granted` could pass for a complete grant. Review of T-004 round 2 found exactly that.
- **Decision:**
  1. `hash = sha256(prevHash + canonicalJson({ ...header, payloadHash }))` where `header` is every `AuditEvent` field except `payload` and `hash`, and `payloadHash = sha256(canonicalJson(payload))`. This is the one formula; SAFETY §2.2 now states it.
  2. A tombstone is exactly `{ redacted: true, payloadHash }`; `Stores.redactAuditPayloads` / `deleteTrip` write that form, and `verifyAuditChain` re-verifies a tombstone in full against its digest. A bare `{ redacted: true }` is an ordinary payload and therefore a `hash_mismatch`. `sealAuditEvent` refuses to seal a tombstone-shaped payload.
  3. The booking-lifecycle facts the verifier needs are hashed header fields, not payload: `AuditEvent.lifecycle = { outcome }` on `policy.evaluated` and `{ complete }` on `approval.granted` (`proposalId` already was a header field). `sealAuditEvent` derives them from `payload.outcome` / `payload.complete` when a caller omits `lifecycle`, so existing writers are unchanged, and throws `invariant_violation` on a missing or invalid outcome, a non-boolean `complete`, a header that disagrees with the payload, or a header on any other event type. The verifier reads only the header (`unknown_outcome` / `unknown_grant_completion` when it is absent or invalid).
  4. The chain has no secret, so a rewrite of every row from some index on, with hashes recomputed, is undetectable from the file alone. `pnpm audit:verify` prints `HEAD group=<id> events=<n> hash=<sha256>` per group and accepts `--expect-head <groupId>=<hash>` (repeatable; a vanished group fails its anchor). The morning report records the heads.
- **Alternatives:** an HMAC with a key from `.env` (a secret the same attacker can read on a single Mac; and it would make `TRAV_OFFLINE` fixtures key-dependent); hash the whole payload and keep legacy bare tombstones trusted (the flaw above); keep lifecycle facts in the payload and forbid redacting lifecycle events (leaks `policySnapshot` and approver ids past "forget this trip").
- **Consequences:** no schema change (rows are JSON; `lifecycle` is an optional field); events sealed before this decision have no `lifecycle` header and would report `unknown_outcome`, acceptable because no production log exists yet. `@trav/core/storage` no longer exports `REDACTED_PAYLOAD`; use `audit.tombstonePayload(original)`.

## D-017: Eval harness policy: `--live` is opt-in, known gaps run and are scored apart, any failing §3 id is hard, deltas are selection-aware (2026-10-22, builder T-020)

- **Context:** T-020 review round 1 found four eval-harness behaviours that were stricter or looser than the docs said, with no recorded decision: when the harness makes live model calls, how scenarios that wait on an unbuilt task are scored, which SAFETY §3 ids fail the run, and which earlier report a run is compared with.
- **Decision:**
  1. **Live is opt-in.** `pnpm eval` is offline unless `--live` is passed AND `TRAV_OFFLINE` is unset AND `TRAV_ANTHROPIC_API_KEY` is present AND the spend guard (`.trav/spend.json`, `TRAV_LIVE_BUDGET_USD`) allows another call. Otherwise it runs offline and the report's Mode line says why. Rubric graders (`TRAV_GRADER_MODEL`) run live only.
  2. **Known gaps.** A scenario marked `pending: "T-xxx"` still runs every step and grader. Its feature failures (and a crash) are scored but not hard. It counts in `overall`, not in `ready`, and is listed under "Known gaps". Its safety graders stay hard. A pending scenario can't also be tagged `regression`, and one that passes everything is flagged so its marker gets dropped.
  3. **Any failing §3 id is hard.** A failing grader result that carries a SAFETY §3 id exits 1, whether or not §3.I lists that id as hard (B3, C5, C7, E5, F3, F4 included). Static architectural check failures (A1, A2, B2, H1, H2) are hard too. A built safety scenario that crashes fails each of its checklist ids. Exit 2 is reserved for harness errors (bad flags, bad scenario files). The root script runs `node --import tsx packages/evals/src/cli.ts` directly (D-015), because a nested `pnpm --filter` would flatten the 2 into a 1.
  4. **Deltas are selection-aware.** Each scenario is compared with the newest earlier summary that contains it. Totals, per-tag scores and "not in this run" are compared only with the newest earlier summary whose selection matches (counts ignored). Static failures are compared with the newest run that ran the static checks. The report says which baseline it used. Held-out scenarios are left out of per-tag scores and the Changes lists, except for safety failures.
  5. **Evidence never quotes a DM.** Grader evidence quotes message text only through `graders/util.ts` `quoteMessage`/`quoteText`, which turns DM text into `[private message, N chars]`. The report's `redact` pass also treats whole DM lines as secrets, as a backstop.
- **Alternatives:** live when a key is present (spends without asking); skip pending scenarios (hides safety regressions in their working steps); hard only on §3.I ids (lets a QR in the group or a minor's roast pass with exit 0); compare with the newest report regardless of selection (a `--filter` run masks the next full run's regressions).
- **Consequences:** CI (`pnpm check`) never spends. A new §3 grader id fails the run as soon as it fires. Reports from filtered runs can sit in `evals/reports/` without corrupting the trend.

## D-019: Approval attempts that do not count are silent; Trav names the approver only when asked; bare text binds to the sender's own proposal (2026-10-25, builder T-007-b)

- **Context:** T-007-b review round 2 found the loop posting "that has to come from Dean. @Dean 👍 to book" for any chat line that named a member next to an approval word, even when nobody was talking to Trav, and tagging an arbitrary member for "everyone's in". VOICE §6.2 says a 👍 from a non-approver is ignored silently (one nudge after 5 minutes at most), SAFETY §2.1 says only the requester's bare "yes" binds, and SAFETY §2.5 says a claim about someone else contributes nothing. The three had never been reconciled into one rule for the loop.
- **Decision:**
  1. **Attempts that do not count are silent.** A 👍 / tap / bound "yes" from a member who is not in the decision's approver set, a bare "yes" / "no" from anyone but the requester, a minor's or guest's attempt, and a claim on someone else's behalf ("Dean said it's fine", "everyone's in") each produce exactly one `approval.invalid_attempt` audit event (`cause`: `not_required_approver`, `not_requester`, `minor`, `guest`, `claimed_for_other`) and no message. The proposal stays pending.
  2. **Trav names the approver only when it was addressed.** If the claim is for Trav (an `@trav` mention, a quote-reply to Trav, or the reply window) and names one member, Trav answers once: "that has to come from Dean. @Dean 👍 to book". An "everyone" claim names nobody, so nobody is tagged. An unaddressed claim in ordinary chat gets no reply, whatever words it carries.
  3. **Binding without a card reference (SAFETY §2.1).** A bare "yes" / "no" binds only to the sender's own pending proposal (two of theirs ⇒ "which one?"); a bare "not me" / "i'm out" binds to the proposal the sender is charged on (an opt-out never spends and only ever yields a fresh card); "everyone's in, book it" is the sender's own attempt and binds only where they are in the approver set. Everyone else must reply to the card, tap it, or name it.
     **Amended by T-066 (2026-10-25): SAFETY §2.1 governs, and a decision entry cannot relax it.** A card-less "everyone's in, book it" binds exactly like a bare "yes": only to the sender's OWN pending proposal (requester), and then only where the requester is in the approver set (else `claimed_for_other`). From anyone else it is `not_requester` (audited with `claimKind: 'everyone'`, silent), even when they are a required approver; it binds only when they reply to the card, tap it, or say it inside the reply window as the normalizer already allows. The requester's own "everyone's in, book it" still counts as their 👍. Two more T-066 refinements (round 2 wording): a claimed approval is text that names a member (or "everyone") with a consent phrase AND either carries an approval word ("book it", "yes", "go ahead", 👍 …) or is an addressed NAMED claim ("@trav dean said it's fine" still gets its audit row and the answer in (2)); "everyone" claims need the approval word. Attendance words (`in`, `down`) are not consent phrases, so "@trav henry's in now too" goes to the roster handler and "@trav everyone's in the lobby, where next?" to the model. The addressed reply to a named claim tags the named member only when they are in `requiredApprovers` and have not yet granted, otherwise the approver(s) the decision still needs ("need a 👍 from @Dean on this one", VOICE §6.2; silent when more than two), otherwise nothing.
  4. **The VOICE §6.2 five-minute nudge ("need a 👍 from @Dean on this one") is deferred.** It needs a scheduled job (`approval_nudge`) and `ScheduledJobKind` in `@trav/core` has no such kind; adding it is outside T-007-b's package boundary while T-030's review is open. Until then the only nudge is the addressed answer in (2). The audit trail already records every non-counting attempt, so the job can be added without changing the loop's contract.
- **Alternatives:** keep the immediate @tag (unsolicited, and it tagged the wrong person for "everyone"); bind any member's bare "yes" to the single pending proposal (a "yes" answering someone else's question becomes an approval); treat "everyone's in, book it" as a claim and reject it even from the requester (it is their own consent plus hearsay; the hearsay is simply ignored); post the nudge on the next turn after five minutes (breaks "one group message per turn" and makes timing depend on chat traffic).
- **Consequences:** `identity.gateApproval` has a `not_requester` cause and an intent-aware binding filter; `loop.routeApproval` takes an `addressed` flag; the eval scenario `identity_claimed_approval` (addressed, `@trav`) is unchanged; `fixtures/chats/barcelona.jsonl` msg_bcn_0036 ("henry's at practice, i'll approve for him. go ahead trav") names no member in a consent phrase and is not addressed by the rules, so it is silent, which that fixture allows; a follow-up task should add the `approval_nudge` job kind to core and the 5-minute post to the loop.

## D-020: Provider requests carry `groupId`; payment refunds carry approval and requester; tickets carry a status; one fixture loader per package (2026-10-25, builder T-059)

(D-018 was skipped because it was absent while another builder's D-019 was already in the file. It may be held by an in-flight task.)

- **Context:** The T-008-a review found that `PurchaseTicketsRequest`, `CreateFlightOrderRequest`, `BookLodgingRequest` and `ChargeRequest` had no `groupId`, so a provider could not compare a request with `ApprovalProof.groupId`. Lodging and flights checked the group only when built with `options.groupId`, and tickets and payments never checked it. `BookingPaymentsAdapter.refund(intentId, key, amount?)` took no approval and no caller, unlike `TicketsAdapter.refund`, so the `booking.refunded` audit event (SAFETY §2.2: `providerRef, refundMinor, requestedBy`) had no provider-side identity behind it. `IssuedTicket` had no state, so only the mock's private bookkeeping knew a ticket had been refunded. Fixture files were read by two separate repo-root resolvers in adapters (`flights/fixturePath.ts`, `transactions/fixtureFiles.ts`) and three ad-hoc readers in core tests.
- **Decision:**
  1. **`groupId: GroupId` is required** on all four purchase/charge requests. Every mock checks it through one helper, `checkRequestGroup` in `mock/payments/proof.ts`. A missing or blank `groupId` returns `invalid_request`. A request whose `groupId` differs from `approval.groupId` returns `approval_invalid` (the code the flights interface already documented for "proof for another group"). Both are typed results and nothing throws. This holds whether or not the adapter was built with `options.groupId`, which remains an extra binding. A same-key replay that names another group returns `duplicate`, never the original order. Ticket refunds, and payment refunds, also refuse a proof from a group other than the one the order or charge was made in. Lodging and flights cancellations already did this.
  2. **`BookingPaymentsAdapter.refund(request: RefundChargeRequest)`** takes `{ intentId, amount?, requestedBy, idempotencyKey, approval }`. It is a request object, not positional arguments, because `requestedBy` and `idempotencyKey` are both strings and easy to swap. Rules: a missing or blank `requestedBy` returns `invalid_request`. A missing, malformed or expired proof, a proof for another group, or a `requestedBy` not in `approval.approvedBy` returns `approval_invalid`. A refund above `maxAmount` returns `approval_exceeded`. One approval funds one action, so neither the charge's own approval nor an approval already used for another refund can fund a refund. Replays are idempotent per key and must match intent, amount, approval and requester.
  3. **`booking.refunded` already exists** in `AuditEventType` (`packages/core/src/domain/audit.ts`), with its payload documented in SAFETY §2.2. `@trav/core` therefore needs no change. The executor writes `{ providerRef: intentId | orderId, refundMinor, requestedBy }` with `requestedBy` taken from the refund request.
  4. **`IssuedTicket.status: 'issued' | 'refunded'`** (`IssuedTicketStatus`). A refund rewrites the order's tickets with `status: 'refunded'`. `getTicketForHolder` answers `not_found` for a refunded ticket and never returns one. The executor DMs tickets only from `getTicketForHolder` (the T-009 contract), so a void QR is never DM'd. We chose this over returning the ticket with status `refunded` and relying on the caller to check, because the first design makes the safe behaviour the default.
  5. **One fixture loader per package.** `@trav/adapters` has `src/mock/fixtures.ts` (`loadFixture`, `loadFixtureText`, `listFixtures`, `fixtureExists`, `isSafeFixtureSegment`), which resolves the repo root through `pnpm-workspace.yaml` and validates segments. It replaces `flights/fixturePath.ts` (deleted) and the file-access half of `transactions/fixtureFiles.ts`, which now holds only JSON validators. Tickets and lodging keep their static JSON imports: their hygiene tests forbid `fs`, and that is bundling, not loading. `@trav/core` has the test-only `src/testkit/fixtures.ts` (`loadFixture`, `loadFixtureText`, `loadFixtureJsonl`, `listFixtures`, `fixtureExists`), which is not exported from the index and is used by `fixtures.test.ts`, `flights/fixture.test.ts` and `safety/test-helpers.ts`. Core production code still never reads `fixtures/`.
- **Alternatives:**

  - A new `'refused'` error code (rejected: `AdapterErrorCode` already has `approval_invalid` for exactly this case, and a new code would ripple into every executor branch).

## D-041: Group ledger notices hang off one repository hook, are a `system_notice` outbound kind, and every expense reaches the group exactly once (2026-11-05, builder T-165)

- **Context:** T-165 wants the group to see one short line for every expense that lands on the tab, whatever the source (chat text, receipt photo, Uber email, card confirm, booking), rendered like iMessage's grey "Dean added Chase to the conversation" subscript where the channel can, as a plain message where it can't, private sources only after the owner's 👍, and notices within ~60s batched. VOICE §3.7 said shared private items reach the group only in the next recap; that rule is replaced (VOICE §3.7, §4.5, new §4.13).
- **Decision:**
  1. **One hook.** `ExpenseRepository.onCreate(listener)` (core, both backends via `groupRepositories.ts`, covered by the shared repository suite) fires after every committed `create`; never for a duplicate, a failed write or a `replace`; a throwing listener cannot undo the write. `packages/agent/src/notices/expenseNotices.ts` subscribes once per agent, so a new ingestion path cannot forget to announce itself and no ingestion module (`booking/request.ts`, `ingest/expenseText.ts`, `ingest/riders.ts`, …) had to change.
  2. **Operations.** `createTravAgent` wraps its public entry points (`handleInbound`, `runScheduled`, `intakeDocument`, both imports) with `notices.around`. Expenses committed while an operation runs are queued; writes outside one (seeding, fixtures, evals' setup) are never announced. When the last running operation ends, the queue is flushed through the agent's normal `sendTurn` (screen, voice lint, lane rules, audit `message.sent` with `systemNotice: true, expenseIds`), after everything the operation sent, and the notices are appended to its `TurnResult.outbound`. A failed notice never fails the operation (`note … · notice_failed:N`).
  3. **Exactly once.** An expense is announced by exactly one group-visible thing. Chat text and receipt photos already post the VOICE §4.4 "logged:" card in the group and bookings post the §4.2 receipt card; those cards are the announcement (the wrapped `sendTurn` records the expense ids a delivered group card carried; booking-sourced expenses are never queued, since their receipt can come a turn later on the after-charge failure path). A second grey line saying the same thing would break VOICE §2 ("never a second message to say the first one is done"). Shared email and card items, and any future path without a group card, get the notice. The Barcelona demo asserts this for every expense on the tab.
  4. **Wire shape.** `OutboundMessage.kind?: 'system_notice'` plus `noticeExpenseIds`; `isSystemNotice()` in core. A notice is group-lane, one line, no card/actions/images/mentions: `sendOutbound` throws on anything else, and the simulator channel refuses it (`invalid_request`), including on `sendDirect`. `ChannelCapabilities.systemNotices` (simulator: true): without it, `sendOutbound` strips `kind` and the channel gets an ordinary short message (audited `noticeDowngraded: true`). The simulator's `TranscriptMessage.systemNotice` / `ThreadMessage.systemNotice` drive the UI's `.system-line.system-notice` row and the CLI's `(notice)` line.
  5. **Text.** `render/expenseNotice.ts` (pure): `<who> added <description> <amount> · <split>`, built from the GroupStore `Expense` only (VOICE §4.13). Batches: grouped by who added them, compact splits, at most 3 named, the rest counted, ≤240 characters.
  6. **Batching.** Inside one flush, expenses are batched by `NOTICE_BATCH_WINDOW_MS` (60s from the first of a batch, inclusive). Across operations: a shared item whose "looks shared?" digest card still has other open lines is held (at most 60s after it landed) so a digest answered tap by tap gives one line, sent after its last answer; a hold past the window goes out at the end of the next operation. No timer or scheduled job: the simulator's clock only moves when the demo moves it, and a timed release would hide the line until then.
- **Privacy:** the text never reads the PrivateStore. The hold reads the owner's pending items only to learn whether their digest is still open; nothing from them reaches the line. `promote()` remains the only private → group path, so nothing private can be announced before the owner's confirmation (tests: `ingest/card.test.ts`, `ingest/email.test.ts`, `ingest/intake.test.ts`, `notices/expenseNotices.test.ts`, the demo).
- **Consequences:** fixtures `msg_bcn_d_0009` / `msg_bcn_d_0010` expect `groupMessages: 1` (the notice). Two different members' shares 30s apart are two lines (each follows its own action at once); merging those would need a delayed send. Channels that can edit or retract messages could later fold a late share into the previous line.
- **Revised in T-165 r2 (review flaws 1-6); these supersede points 2, 3 and 6 above where they differ:**
  1. **Holds end on the scheduler.** A held notice (a digest share waiting on the rest of its digest, a booking waiting on its receipt) gets an `expense_notice` job (new `ScheduledJobKind`, payload `{ expenseIds }`) at `at + windowMs`. `runScheduled` hands it to `notices.release(job)`; the line goes out when that operation ends, so a chat that goes quiet still gets it. An unrelated operation no longer releases a hold. A hold that ends early (the digest closed, the receipt went out, the share was undone) cancels its job. The job carries the expense id and the audit log (`message.sent` with `systemNotice` and `expenseIds`) says whether it was announced, so a job for an expense this process no longer has queued still announces it exactly once. The v0 scheduler itself is in memory, like every other job (a durable scheduler is the real-deployment TODO for all of them).
  2. **No raw descriptor.** When the card provider gave no `merchantName`, `displayName` still shows the owner the statement descriptor in their DM (recognition), and the pending item is flagged `merchantFromDescriptor`; `promotable()` then puts the charge on the tab under `groupSafeChargeName(category)` ("ride", "card charge", …). The tab entry is group data (notices, recaps, Wrapped, settle-up), so the descriptor never reaches the group.
  3. **Undo corrections.** `ExpenseRepository.onUndo` (core, both backends, repository suite) fires after a committed `replace` that turns a logged expense undone. An expense a notice announced gets one correction line, `system_notice` with `noticeCorrection: true` ("Crowley took Uber €23.40 off the tab", VOICE §4.13); one still queued or held is dropped silently; one a group card announced is left to that card's own undo reply.
  4. **Bookings are queued.** A booking's tab entry is queued like any other and held until its group receipt card is delivered (then dequeued, job cancelled). A receipt the screen held back or that failed to send leaves the hold to its job, so the booking still reaches the group exactly once.
  5. **Downgrade strips every notice field.** `plainMessage` drops `kind`, `noticeExpenseIds` and `noticeCorrection`; the audit keeps them.
  6. **Per-group flushing.** Each operation runs in its own `AsyncLocalStorage` context that records the groups its writes touched. When it ends, a group is flushed unless another still-running operation touched that same group (that one flushes it). An operation in another chat never delays this chat's line.

## D-042: Approval and auto-buy are positive whitelists decided in code, not blocklists (2026-11-05, builder T-182)

- **Context:** T-173 hardened the offline ask reader (`booking/request.ts`) with fail-closed blocklists over two rounds, and each review found new phrasings that read as asks ("…, i don't think so", "piotr if he wants", "henry's also sick"). T-168 will turn an explicit ask into a purchase with no confirm card, so "what counts" has to be a narrow thing the code recognises, with everything else falling back to the one-tap card. Approvals had the same shape: T-132 once counted "i don't approve for the group", and a card-less "everyone's in, book it" counted as the requester's 👍 (D-019, T-066).
- **Decision:**
  1. **Approval whitelist** (`packages/agent/src/approval/whitelist.ts`). A proposal is approved only by a 👍 tapback on its card, a tap on its Approve button, or a text reply that, after normalizing case, curly quotes, whitespace, trailing punctuation, a few warm emoji (🙏 🎉 🙌 🔥 💯 😊 ✅) and a leading "@trav"/"trav,", is exactly one of `APPROVE_REPLIES` (yes, yep, go, book it, do it, approve, approved, i approve, yes book it, yes do it, yep book it, yep do it, yes please, yes pls, 👍). Binding is unchanged (quote-reply on the card, Trav's question in the reply window, else the requester's own single pending proposal; SAFETY §2.1). `routeApproval` (`loop.ts`) is the one place a text approval reaches `ApprovalHandler.handle`, and it refuses anything `approvalCounts` rejects. Never an approval: negations, qualified yeses ("yes but not for me"), approvals said for others ("approve for him", "i approve for me and henry"), sarcasm ("oh yeah sure"), a laughing/eye-roll emoji ("yes 😂"), a thumb that contradicts the words ("yes 👎"), a quoted or forwarded old "yes" (quote marks, ">", "fwd:", "Dean: yes", `InboundMessage.forwarded`, or a "yes" quote-replying a member's message instead of the card).
  2. **What a refused approval does.** It is audited `approval.invalid_attempt` (`not_whitelisted`, or T-132's `claimed_for_other` row with `partial: true` kept and `whitelisted: false` added). When it was said to Trav (quote-reply, reply window, @trav) Trav asks back once: `not booked. 👍 the card or reply "yes" to book it`; `not booked. reply "not me" to drop out, or "yes" to book it` when it sounds like the sender wants out; `not booked. everyone approves for themselves: 👍 the card or reply "yes"` for an approval said for others. A short "near miss" (`nearMissKind`: an approval word plus only words from a small closed vocabulary or member names) is routed the same way; anything with another word goes on through the loop, so a real request is never swallowed. **Supersedes** D-019/T-066's "card-less 'everyone's in, book it' counts as the requester's own 👍" and T-132's "the sender's own part of 'i approve for me and henry' counts": neither approves now.
  3. **Auto-buy whitelist** (`packages/agent/src/booking/autoBuy.ts`, `autoBuyVerdict` / `autoBuyEligible`). A positive grammar (written out in the module comment): addressed to Trav at the start, an imperative buy verb (get, grab, book, buy, snag, reserve, purchase), exactly one venue by a non-generic term, a party (us / everyone / all of us / the group, optionally "except <names>"; "the N of us"; "for <names>" that include the sender, as me/myself or their own name; a count; amended by D-046: any party that leaves the sender out, including "except me" and ", not me", is `party`), optional out clauses for a member ("Henry's sick", "Henry can't make it", "Henry isn't coming", with a closed list of out-states), and only whitelisted tails (thanks, pls, lol, haha, cheers, asap, "when you get a sec", warm emoji). Names in the object slot ("get chase and me razz tickets") are not in the grammar (T-173 r2 #3). Then the party must resolve against the roster (members only, nobody both in and out, every stated count equal to who it names, at least one person, the sender among them), and `parseBookingRequest` must read the same quantity, out-list and names. Anything else is `eligible: false` with a reason, and T-168 must show the confirm card. Price caps, refundability, minors and idempotency stay with `ApprovalPolicy` and the proposal service: the predicate only says the words were unambiguous. T-168 wires it; this task only exports and tests it.
  4. **Reader fixes** (T-173 r2 #1–#3, `booking/request.ts`): a negation takes the ask back by default, in any clause, except `believe`/`wait`/`miss` and an out-reason (`make it`, `come`, `join`, `feel`) whose subject is one other person; a strong conditional anywhere ("and piotr if he wants") or a weak one about a person makes it no ask; `objectList` keeps the sender for "me"/"myself" and reads "and" as a list joiner (a venue word set that held "and" had stopped the list at "chase").
  5. **Offline model.** The loose T-007 `bookingIntentResponder` is out of the default fallback chain: it proposed "…, Henry's sick. actually i don't think so" after the reader had said no. `booking_request_v1` alone reads asks offline.
- **Evals:** `packages/evals/scenarios/approval_whitelist.json` (dev split, tagged `safety` and `regression`): the near-miss approvals on the flagship card, ending in one exact "yes" that buys once; the T-173 r2 repros through the runtime (no purchase); and the `auto_buy` probe over `fixtures/safety/auto-buy-asks.json`, graded by `auto_buy_whitelist` (false positives A3 hard, party on eligible asks A9, recall scored).
- **Consequences:** fewer things approve by text. "yes i approve for all of us" now needs a plain "yes"; "everyone's in, book it" needs "book it". "get the 5 of us razz tickets, Henry's sick, isn't that sad" is no longer read as an ask (the negation default). Any new phrasing that should auto-buy is a deliberate grammar change with a test, never a regex tweak.
- **Revised in T-182 r2 (review `tasks/reviews/T-182-r1.md`):**
  1. A near miss never covers a party edit: a message that names a member, says me/him/her/them/us + too/also, or has without/except/only goes on through the loop (roster and proposal flows), never gets the "not booked" line.
  2. A near miss with a no in it ("i don't approve", "no don't book it", "don't do it") gets `not booked. reply "no" to drop it, or "yes" to book it`.
  3. `AutoBuyInput` takes `lane` (required; only `group` can auto-buy, since a DM's "us" can't mean the group), `forwarded` and `quotesMessage` (either ⇒ `quoted`). "us" / "the N of us" / "everyone" from a sender in `alreadyOut` is `party`, never the others without them.
  4. As a clause of its own, a bare "no NAME" or "but NAME" is not an exclusion (it can be read another way); "not NAME", "but not NAME", "except NAME" still are, as is "everyone but NAME" inside the party.
  5. **Orchestrator:** "lol" and "haha" are not auto-buy tails (sarcasm markers); those asks get the card. "thanks", "pls", warm emoji and "when you get a sec" stay.
  6. Reader: "nobody", "no one" and "none of us/you/them" are negations (take the ask back); a pronoun said to be out ("…, he can't make it") with nobody named out and no named list is no ask.
  7. Card `textAliases` (`booking/proposals.ts`, `loop.ts`, `render/common.ts`) are built from `APPROVE_REPLIES` / `DECLINE_REPLIES` / `NOT_ME_REPLIES` (`*_TEXT_ALIASES`: the replies minus the 👍/👎 glyphs), so they can't drift.

## D-043: Settle-up is Sent → Got it with locally built pay links; only the payee's word clears a debt; payment profiles are owner-private (2026-11-05, builder T-166; supersedes D-034)

- **Context:** D-034 let a payer's 👍 on the final settle card reduce what they owe, and nothing could take it back. Dean (T-166) wants the person getting the money to say it arrived, pay links so paying is one tap, and Trav to know which apps each member uses without asking twice.
- **Decision:** (1) **States.** `SettlementPayment.status` is `sent | received | undone` (`marked_paid` rows from D-034 read as `sent`). `SettlementRepository.update` changes state only, never who, what or which card. Only `received` reduces balances (`isSettlementCleared`, applied in `tripMoney`, so every reader agrees). (2) **Taps** (`agent/settle/actions.ts`): the payer's [Sent], 👍 or "sent" makes their rows on that card `sent` (the row reads "Chase says sent €42 to Dean", still owed); the payee's [Got it], 👍 or "got it" makes what was said sent to them `received`, or records `received` directly for their one open row with no Sent (a bare Got it with several rows and nobody said sent asks instead of guessing). A 👍 is Got it when someone said sent to the reactor, else Sent if they owe, else Got it if they're owed. [Undo] / 👎 / "undo" takes back the tapper's own last step: payee `received` → `sent` (or `undone`), payer `sent` → `undone`; a payer can't undo what the payee confirmed. Guests, minors, bystanders and second taps change nothing. Every change writes `settlement.sent|received|undone` with `moneyMoved: false`. D-034's tab-moved rules (a) to (c) still hold. A [Paid] tap on a pre-T-166 card is a Sent. (3) **Payment profiles** (`core/domain/payments.ts`): apps, favourite and handles in a new owner-private `payment_profiles` table (`PrivateStore`, SQLite migration v3, deleted with the partition). Members set them in DM ("my venmo is @chase-w", "venmo and zelle, venmo's my fave"); a handle said in the group isn't stored. Audit rows are owner-visible and name rails, never handles. **Ask once:** Trav DMs "which apps do you use?" at sign-up (member joined) or the first time they owe or are owed money, whichever is first. `askedAt` is written only after the DM goes out, and anyone who already told Trav something is never asked. Never a guest or a minor. (4) **Rail choice** (`core/payments.chooseRail`, pure): among rails both have, the payee's favourite, then the payer's favourite, then the payee's order, skipping handle rails the payee gave no handle for. A payer with no profile defers to the payee. Nothing shared ⇒ the payer is told and offered the payee's handles; a shared rail with no handle ⇒ the payer is told and the payee is asked once in DM. (5) **Pay links** (`core/payments.payLink`): built locally, never fetched. Venmo `venmo://paycharge?txn=pay&recipients=…&amount=…&note=…`; Cash App `https://cash.app/$tag/amount`; PayPal `https://paypal.me/name/amountCUR`; Zelle has no link, so the payee's contact is shown to copy. The note is sanitized so it can't add parameters. Dollar-only rails get the amount at the mock reference rate (`convertByRate`, BigInt, half away from zero), shown both ways ("€20.70 (≈$22.62)"); no rate ⇒ the link opens with the payee only and the DM says to type the amount. (6) **Privacy:** the group card names the rail only ("Chase → Dean €42 · venmo", footer "pay details are in your dms."); handles, contacts and links go only to that transfer's payer, in DM, and are re-sent only when rail, amount or handle changes (deduped on owner-only `settlement.pay_details_sent` rows that hold handle digests, never handles).
- **Consequences:** a payer's word alone never clears money, so D-034's "a mistaken 👍 can't be taken back" is gone. VOICE §4.6 gains examples D (profile), E (payer DM) and F (Sent → Got it). Nudges, disputes and auto-confirm stay with T-037. No money moves on any path, and no payment app is called.

## D-044: Approval tiers: the policy auto-approves only an ask decided in code (2026-11-05, builder T-168)

- **Context:** Dean (2026-11-05): Trav should buy what people clearly asked for, offer a choice when the options really differ, and keep the explicit approval for big things.   5. **Receipt** (VOICE §4.2): a purchase with no card adds one line saying on whose word and under which cap: `bought on Dean's ask, under the €500 auto-buy cap` / `bought on Dean's pick, …`. The refund terms stay on line 2. No undo is promised (v0 has no refund flow; T-050).

A city with no catalog falls through to the model.
  4. **Places are a read-only adapter** (`VenuesAdapter`, `packages/adapters/src/interfaces/places.ts`; mock over `fixtures/places/<city>.json`): price level 1–4, typical spend per person in minor units, `adultsOnly` for bars. No schema has a field that approves, buys, pays or names a price.
  2. **Code validates every field** (`validate.ts`), whatever the schema promised: unknown or missing keys, wrong types and out-of-range values reject the call. Amounts are decimals as written and must convert exactly to integer minor units of their currency (`parseDecimal`, BigInt; `16.805` EUR or `100.5` JPY counts as "not stated" and is asked for, never rounded). Names must be current, non-guest trip members (id, "me", or one case-insensitive display-name match): an unknown payer or an unknown name in who's-in becomes the flow's one question; an unknown name anywhere a share is fixed (fixed shares, weights, line-item claimants) rejects the whole call. A rejected call, no call, or several calls go to the chat loop.
  3. **The same flows act on the read.** A validated expense goes to `chatExpense.handleInterpreted` (the same `evaluateDrafts` checks, one question, ledger notice); one attendance change goes to the one roster write path (`handleRosterMessage({ interpreted })`: the minors rule, `kept_off`, the headcount check, re-proposal); `approval_reply` only ever becomes a `NearMissKind` for `routeApproval`, which asks back and never grants. Approval stays the D-042 whitelist on the raw text, eligibility stays the handler's (an out or excluded member is refused), auto-buy stays `autoBuyVerdict` (code, from the member's words), and every purchase goes through `ApprovalPolicy` and the audit log.
  4. **Fast paths that stay regex** (read-only or already safe): the approval whitelist and claimed-approval detection, near-miss replies, the roll call ("who's in tonight?"), balance asks ("settle now", "who owes who", "what do i owe"), suggestions (D-045), and the slot-fill answer to Trav's own open expense question. Everything else addressed to Trav falls through to `interpret_v1`, then to the chat loop. Two guards skip the read entirely and hand the message to the chat loop (T-183 r2): a booking ask the deterministic reader recognises (`parseBookingRequest` with the bundled venue index), so a misread can never turn "get the 5 of us Razzmatazz tickets, Henry's sick" into a roster line with no proposal or a ledger entry for a purchase that never happened; and a whole-message forward (`event.forwarded`), which is never the forwarder's own words (SC-12). A model tool call also never sets `allAdultsConfirmed` (SC-13): `request_settings_change` returns `needs_confirmation` pointing at the typed "@trav everyone's 18+".
  5. **Booking calls are strict too.** `propose_booking`'s schema is closed and bounded (`PROPOSE_BOOKING_SCHEMA`) and `parseProposeInput` refuses any other key (`closedKeys`).
  6. **Offline stays deterministic.** `AgentDeps.interpretation` defaults to `model_first` with a live client and `parser_first` offline. In `parser_first` the readers act as the scripted model: their read is encoded as the same `record_expense` call (`encode.ts`) and goes through the same validator. A round-trip test over every labeled phrasing proves the schema can say everything the readers can, so offline behaviour (tests, CI, the demo) is unchanged. `modelFirst.test.ts` drives the real runtime with a stand-in live client and no network.
  7. **The parser tests are eval cases.** `interpretCases()` (`interpret/cases.ts`) turns `fixtures/expenses/{phrasings,text}.json`, the Barcelona chat and the roster reader's phrasings into cases whose expected interpretation is the readers' read; `gradeInterpretation` compares money facts and roster changes, not wording. Exported from `@trav/agent` for the evals package.
  8. **Prompts.** `prompts/index.ts` is now three reviewable sections (`VOICE_SECTION`, `TOOLS_SECTION`, `SAFETY_SECTION`) under the unchanged ids `group_chat_v1` / `dm_chat_v1` (script keys don't hash prompt text). `prompts/interpret.ts` is the `interpret_v1` prompt. A test keeps the tools section in step with `V0_TOOL_NAMES`.
- **Consequences:** live, an addressed message that isn't a fast path costs one extra main-model call (the read) before the chat turn, when there is one. A model misread can at worst produce a question, a refused call or a chat turn: it can't log an amount that isn't whole minor units, put a share on a non-member, write a guest or a minor onto an adults-only plan, or approve or buy. Not yet done: wiring `interpretCases` into `packages/evals` as a live scenario family (outside T-183's package scope), and the conversation-designer and safety-reviewer passes over the new prompts.

## D-048: Channels degrade by capability flag; relay lines get pacing and burst debounce as decorators (2026-11-05, builder T-069 + T-071)

- **Context:** the iMessage relay work (T-169, T-187) needs the agent to behave on a line that has tapbacks but no buttons (an all-iPhone relay group) and on one that has neither (a group that fell back to MMS when an Android member joined), and the line itself must stay under Apple's opaque spam signals (volume and send-to-receive ratio; research/connectors.md "iMessage group access (2026-11-04)"). T-183 is concurrently rewriting `packages/agent`, so this lands in `packages/adapters` only.
- **Decision:**
  1. **Capability flags, not vendor names.** `ChannelCapabilities` gains `seesAllGroupMessages`, `typingIndicator`, `readReceipts`, `canRenameGroup` and `groupTransport: 'imessage' | 'rcs' | 'mms'` (additive; `kind` is unchanged). Rendering and routing read the boolean flags only; `groupTransport` is for notices (T-072) and logs. `channel/profiles.ts` names three flag sets: `simulator` (the default, unchanged behaviour), `imessage_relay_group` (text + images, tapbacks, threads, typing, read receipts, member changes; no buttons, cards or system notices; max 32) and `mixed_group_mms` (text + images only). `createSimulatorChannel({ profile })` runs under one, with `capabilities` overrides on top; under a profile without reactions the simulator refuses member tapbacks like it already refused button taps.
  2. **Wire text for what the channel can't do.** `textForChannel` (`channel/fallbackText.ts`, pure) rewrites only answer instructions on the way out: without reactions `👍 to book` → `reply "yes" to book`, `need a 👍 from @Dean` → `need a "yes" from @Dean`, `👎 to undo` → `reply "undo"`; without buttons `tap Sent` → `reply "sent"`; the looks-shared digest's `👍 each one you want on the tab` → `reply with the numbers you want on the tab`. Only a message that asks for an answer is touched (it carries `actions`, or a booking-proposal / expense-confirm / options / settle-up card); anything else goes out exactly as written, and quoted text (`"…"`, `“…”`, a `>` line) is never rewritten. The reply word is the message's own action alias (so the keyword matcher and the D-042 whitelist accept it), with VOICE §6.2 defaults. The envelope (`OutboundMessage.text`, `card.fallbackText`) is untouched, so `fallbackText === text` still holds for the agent; the simulator records the rewritten text and marks the send `degraded`. A future agent change can word messages per capability itself; this stays as the safety net for any phrase it misses.
  3. **Pacing is a decorator** (`withOutboundPacing`, `channel/pacing.ts`): per-line cap of 500 sends per rolling 24h, of which the last 20 are reserved for critical messages (so the cap never holds an approval prompt while the line has room), send-to-receive ratio `sends ≤ max(10, floor(3 × receives))` over 24h (receives are member messages, tapbacks and taps, deduplicated by id), a content-free group reply ("got it", "done") goes out as a 👍 tapback on its target where reactions exist. Over the limit a text or DM is queued and the call returns `ok` with `queued: true`; the queue drains by priority (approval prompts, i.e. a message with actions or a proposal / confirm / options / settle-up card, and `urgent` messages first; then replies and DMs; then proactive messages), FIFO within a class, on every inbound event (before the event reaches the agent, so a queued prompt lands before Trav's next answer), every send, `tick()`, or an injected timer. A message accepted as `queued` can still be lost in exactly three ways, each audited as `message.budget_dropped` with a `reason` (reusing that type keeps core's audit union unchanged) and each reported once to the host's `onFailure` hook: `queue_full` (past 200 entries a proactive message goes; past 1,000 critical + normal entries the oldest normal one goes; a critical one is never dropped for room, the queue grows instead), `expired` (a queued message whose `expiresAt`, or a proposal card's `holdExpiresAt`, has passed is withdrawn rather than delivered late with a dead hold), and `send_failed` (the inner channel refused it when it finally went out: a `retryable` refusal goes back to the front of its class and is retried after 30 s × attempt, up to 3 tries; the final failure of a normal message reaches `onFailure` but is audited only when critical). A refused proactive message returns `rate_limited` up front (`reason: "line_pacing"`). An over-limit tapback returns `rate_limited` (a late 👍 is noise). A resend of an id that is queued, on the wire, or already sent never takes a second slot or reaches the wire again. Remembered ids and the failure list are capped at 5,000 each.
  4. **Burst debounce is a decorator** (`withInboundDebounce`, `channel/debounce.ts`): consecutive messages from one sender in one conversation within 3 s of each other (held at most 10 s) become one `InboundMessage` (first id, text joined by line breaks, and `mergedMessageIds` with 2+ ids; a lone message is delivered unchanged, without the field). Senders are never merged, and a message with attachments is never merged: it flushes the pending burst and goes at once as its own event ("yes" then a photo is two events). Any other event in the conversation flushes the burst first, so per-conversation order holds; redeliveries of any merged id are dropped. **Merging can create an exact approval**: the D-042 whitelist collapses line breaks, so "do" + "it" or "yes" + "please" merged read as "do it" / "yes please". The agent must therefore refuse any event carrying `mergedMessageIds` as an exact text approval and ask back instead; that agent-side check is a follow-up (the coordinator owns it, since `packages/agent` is being edited by T-196/T-198), and until it lands a relay line should not run the debounce in front of approvals.
  5. **Composition and time.** Relay lines use `withInboundDebounce(withOutboundPacing(channel))` so the ratio counts every message a member sent; `withMessageBudget` can wrap the result as before. Both decorators read time from the injected `Clock` only; without `timers` the host calls `tick()` (tests, simulator), a server passes `systemChannelTimers()`.
- **Consequences:** the Razzmatazz flow passes on both profiles through the real runtime (`apps/simulator/src/demo/channelProfiles.test.ts`), including the card path approved by a plain "yes" on MMS. The rewritten instruction lines are new user-facing wording derived from VOICE §6.2 (`reply "yes"`); conversation-designer should confirm them. Because only answer messages are rewritten, an instruction line sent without actions (the "need a 👍 from @Dean on this one" nudge, "@Dean 👍 to book", `not booked. 👍 the card or reply "yes"`) still says 👍 on MMS; a plain "yes" still works there, and the agent should word those per capability. Open: proactive messages can starve behind a long reply backlog until the backlog clears; the pacing queue and the seen-id sets are in memory (T-185 persists runtime state); iOS turns a tapback in an SMS/MMS thread into a text like `Liked "…"`, which nothing parses yet (T-169).

## D-049: `pnpm eval:live` is the one explicit way past `.env`'s TRAV_OFFLINE; each live run carries its own cap (2026-11-05, builder T-184)

- **Context:** `.env` ships `TRAV_OFFLINE=1`, so tests and CI stay offline, and `pnpm eval --live` refuses to go live while `TRAV_OFFLINE` holds any value (`0` included). Before this, running a live eval meant hand-exporting the env file and editing the offline flag. T-184's first live run also needed a per-run stop below the $45 guard budget.
- **Decision:** (1) `packages/evals/src/live.ts` (`pnpm eval:live`) reads the repo's `.env` (or the file `TRAV_ENV_FILE` names) and lets shell variables win. It drops only the **file's** `TRAV_OFFLINE`: a `TRAV_OFFLINE` set in the shell keeps the run offline, and `--preflight` says that is why. It never touches `process.env` or the file. It always passes `--live`, plus `--max-spend 10` unless the caller sets a cap. The key gate and the spend guard (`TRAV_LIVE_BUDGET_USD`) still apply to every call. (2) **One budget.** `TRAV_STATE_DIR` defaults to the `.trav` next to the env file, so a worktree using the main checkout's `.env` spends against the main checkout's `.trav/spend.json`. If the resolved spend file is anything other than the main checkout's (found through git's common dir), or no checkout is found, `eval:live` refuses: exit 2, or under `--preflight` a "would REFUSE" line and exit 0. Without this, a worktree would silently start a fresh $45 budget. (3) `--max-spend <usd>` stops starting new scenarios once the run has added that much to the guard's total. It is checked between scenarios, so a scenario already running finishes. The report states where the run stopped and relabels its selection, so a cut-short run never becomes the baseline of a full one. (4) `--preflight` prints the mode decision, which gate blocks live, and the spend so far, then exits without calling anything. (5) The script sets `NODE_USE_ENV_PROXY=1` so Node's fetch uses `HTTPS_PROXY` when one is set (the overnight sandbox needs this). Without a proxy it does nothing. (6) Report summaries record Trav's model calls per response source (`modelCalls`), so `compare.ts` can show per area how many live calls a score rests on. An area with none took the deterministic path.
- **Consequences:** `pnpm eval` and `pnpm test` work exactly as before. A live eval is one command that can't spend more than its cap plus one scenario. Rubric grading costs about $0.025 per Opus call, four per scenario, so a full 160-scenario live run with rubrics costs about $24, well above the roughly $8 the Trav calls cost.

## D-050: The iMessage relay is a vendor-neutral core plus pure vendor modules; the simulator runs over it through a signed-webhook loopback; live needs three gates (2026-11-05, builder T-169)

- **Context:** T-169 puts Trav in an iMessage group through a relay vendor (Photon first, Sendblue second). The whole Barcelona flow has to play locally, with no way to reach a real vendor by accident. D-048 already supplies the capability flags, wire fallback text and pacing decorators.
- **Decision:**
  1. **Core and vendor split.** `channel/relay/core.ts` (`createRelayChannel`, `kind: 'imessage_relay'`) owns everything vendor-neutral: the webhook size cap, the signature check, dedupe on vendor message and event ids (bounded at 10,000), and the Trav id ↔ vendor id map (so a 👍 on a vendor id reaches the agent as a 👍 on its own message). It sends each Trav message id at most once (an in-flight resend shares one promise). It retries at 500 ms × 2ⁿ, capped at 8 s, honoring `Retry-After`, 3 tries; for vendors without idempotency keys it retries only `429` and `503`. It also renders QR data URLs to PNG through a media host and sends each card as its `fallbackText`. A vendor module (`vendors/photon.ts`, `sendblue.ts`) is pure: `verifyWebhook`, `parseWebhook`, `buildSend`, `parseSendResponse`. A Sendblue tapback that arrives as `Liked “…”` text is matched to the one Trav message it quotes; an ambiguous quote stays plain text.
  2. **One transport seam, one live path.** The core sends through an injected `RelayTransport`. `createLiveRelayTransport` (`config.ts`) is the only code that calls `fetch`, and it refuses any URL off the vendor's `https` origin. `createRelayFromEnv` builds it only when `TRAV_CHANNEL=imessage_relay`, `TRAV_RELAY_LIVE=1` and the vendor key(s) are all set; otherwise it uses the mock relay's transport. A test scans the relay sources so no other file can reference `fetch`. Live mode with an empty webhook secret refuses every delivery (fail closed).
  3. **Loopback for the simulator.** `mock/relay/loopback.ts` puts the members' phones (the simulator "world") on one side of the mock relay and `RelayChannel` on the other. Each member action becomes the vendor's exact signed webhook bytes. Each Trav send becomes the vendor's HTTP request to the mock, which validates it the way the vendor would and records it. The simulator gets a `channelFactory` seam (`LoadAgentOptions`), so `pnpm relay:dev` and `pnpm demo:barcelona --relay[=vendor]` run the same runtime over it. In the `overlay` view a button tap is never sent as a tap. It is played as the member's iMessage action: a 👍 or 👎 tapback, a text alias such as "sent", or an option number. The `phone` view refuses taps. `apps/simulator/src/server/relay.ts` always uses the mock, whatever the environment says.
  4. **Receiver.** `channel/relay/http.ts` binds 127.0.0.1 only (`listenRelayWebhook` rejects any other host). It refuses non-loopback `Host` headers (DNS rebinding) unless built with `loopbackHostOnly: false` for a tunnel, caps bodies at 1 MB, and acks as soon as a delivery is accepted.
- **Consequences:** the Barcelona demo (58 checks) passes over both mock vendors (`apps/simulator/src/server/relay.test.ts`). The vendor payload shapes were reconstructed from public descriptions, not real traffic, so the fixtures must be re-recorded before going live (docs/RELAY.md). Dedupe, the id map and pacing are still in memory (T-185), and so is the media host (T-188). The inbound debounce stays out of the relay path until the agent refuses merged approvals (D-048 §4). On Sendblue, an unthreaded "sent" is not bound to the settle card yet (agent follow-up).
