# T-185 — Persist runtime state

**Verdict:** r1 CHANGES_REQUESTED (1 major, 3 minor), r2 **APPROVE** (4 minor).
**Commits:** e292f31 (build), bd42176 (r1 fixes). Decision D-054.

## What shipped
- `GroupStore.runtime` on both backends: state entries, a capped seen-event-id set and the scheduler's job queue. DM state lives in the owner's private partition. Migrations V4 (tables) and V5 (`trip_id` on state rows).
- `agent/state/persisted.ts`: a write-through cache. Every in-memory map from the task goes through it in `loop.ts`. `createTravRuntime` uses the stored scheduler by default.
- Cards with a QR are never persisted. `deleteTrip` deletes the trip's runtime rows and queued jobs. `TravAgent.forgetRuntimeState({memberId}|{tripId})` evicts cache entries. The card index and the nudge sets are capped at 1000. Guest handles are stored as a per-group sha256 that lapses after 30 days.
- The acceptance test kills the runtime mid-approval and restarts it over the same sqlite file. The 👍 then buys exactly once (one purchase, one charge, a 5-way split at €18 each), and a replayed event id is a no-op.

## Verification
`pnpm check` 6628 tests green; `TRAV_OFFLINE=1 pnpm demo:barcelona` 58 of 58. The reviewer ran V5 on a real v4 file, including a rollback in the middle of the migration, and dumped every table looking for QR data.

## Open (r2 minors → T-225)
1. `forgetRuntimeState` doesn't drop the memory-only ticket cards, so the QR can still be read in the same process after a forget. Nothing reaches disk.
2. `memoryCardGroup` (loop.ts:888,1200) is never trimmed.
3. The guest hash has no secret, so a phone number can be brute-forced from the file. The audit log already stores raw sender ids (SAFETY §2.5). Use an HMAC with a per-install key.
4. Lapsed `guest_told_h` rows are only removed by the cap, never by age.
Also from D-054: settings, ticket-choice and flight-plan stores are still in memory; `recent` lines aren't deleted per trip; no product caller of forget yet (T-045).
